# 预处理脚本对数据集质量的评估报告

生成日期：2026-03-30

## 1. 报告目的

本文档基于当前仓库中的预处理与质量评估脚本，对四个子数据集的可训练性、前景分割可靠性、背景纯净度以及高光监督信号进行整理与核查。报告目标有三点：

1. 说明预处理脚本到底评估了什么，以及这些统计与训练配置之间的关系。
2. 检查现有统计结果是否自洽，识别容易被误读的字段。
3. 给出一份可直接用于论文写作或组内汇报的质量分析结论。

本报告主要依据以下文件：

- `scripts/precheck_subdatasets.py`
- `scripts/validate_ready_datasets.py`
- `scripts/assess_dataset_quality.py`
- `logs/dataset_quality_20260328_0933/dataset_quality.json`
- `logs/dataset_quality_20260328_0933/dataset_quality.md`
- `logs/dataset_validation_20260328_0945/dataset_validation.md`
- `subdataset_backups/ready_20260328/READY_SUMMARY.json`

## 2. 核心结论

当前四个 ready 子数据集在当前训练配置下整体质量是可用的，且没有出现会直接阻断训练的结构性问题。

可以直接下结论的点有：

1. 四个子数据集的 ready 数据都能通过 dataloader 级验证，训练与验证各 split 的批次读取正常。
2. 四个子数据集采样到的样本均成功获得显式前景掩码，`mask_fallback_ratio=0`，说明没有退回到白底阈值掩码。
3. `background_whiteness` 均接近 1，表明白背景较稳定，适合当前前景优先与高光监督流程。
4. `random_lighting_coverage=1.0` 且 `missing_lighting_ratio.any_missing=0.0`，说明当前训练真正依赖的照明条件文件在采样范围内是齐全的。
5. 四个子数据集均未触发脚本中的自动质量告警规则。

同时也有两个需要写清楚、避免误读的点：

1. `image_name_match_ratio=0.8889` 不是数据错误，而是统计口径使然，因为对象目录里除了目标图像外，还包含 `random_lighting_*.png` 和 `*_normals.png`。
2. `hdr_raw_missing=1.0` 不应被解释为照明数据缺失。当前 ready 数据中的 `HDR_raw` 目录存在，但其命名方式与训练时逐图匹配的 LDR/HDR-rescaled 文件不同，因此该字段在当前脚本定义下恒为缺失，而 `any_missing=0.0` 才是判断训练是否受影响的关键指标。

## 3. 评估链路与脚本职责

### 3.1 预检查：`precheck_subdatasets.py`

该脚本面向原始子数据集，作用是在进入 ready 阶段之前，对样本进行抽样诊断。它会：

1. 采样对象和视角图像。
2. 解析前景掩码，若不存在显式掩码则回退到白背景阈值法。
3. 按当前高光阈值逻辑计算高光掩码及相关统计。
4. 检查 LDR、HDR-rescaled 和 HDR 文件的完整性。

这个阶段更像上游“筛查”，用于快速发现原始数据是否适合纳入后续数据构建流程。

### 3.2 ready 数据验证：`validate_ready_datasets.py`

该脚本不是做图像统计，而是直接实例化 `NeuralGafferTrainingData`，对训练集和多个验证 split 跑若干个 batch。它回答的是“这些 ready 数据能不能被当前训练管线正常读取”。

当前验证报告 `logs/dataset_validation_20260328_0945/dataset_validation.md` 显示：

- `official_2000`
- `ecommerce`
- `landscape`
- `three_future`

这四个子数据集在 `train`、`training_object_with_unseen_envir`、`unseen_object_with_random_area_light_condition`、`unseen_object_with_seen_envir`、`unseen_object_with_unseen_envir` 五个 split 上都通过了批次测试。

### 3.3 ready 数据质量评估：`assess_dataset_quality.py`

当前论文与本报告实际引用的质量统计，来自这个脚本。

和 `precheck_subdatasets.py` 相比，它有两个更贴近论文实验的特点：

1. 直接作用于 `logs/ready_subdatasets_20260328` 下的 ready 数据。
2. 高光统计配置与当前主方法保持一致，包括：
   - `foreground_background_threshold = 0.96`
   - `highlight_use_quantile_threshold = True`
   - `highlight_quantile = 0.88`
   - `highlight_min_threshold = 0.02`
   - `highlight_max_threshold = 0.2`
   - `highlight_quantile_blur_sigma = 1.0`
   - `highlight_relative_mode = difference`
   - `highlight_local_kernel_size = 15`

因此，这个脚本输出的高光统计不是一般意义上的“图像亮点统计”，而是“在当前训练监督定义下，该数据会产生什么样的前景与高光监督信号”的快照。

## 4. 质量指标含义

`assess_dataset_quality.py` 统计的核心指标如下：

1. `foreground_area_ratio`
   表示前景掩码面积占整张图像的比例，可用于衡量目标主体是否过小。

2. `background_whiteness`
   在背景区域取 RGB 最小通道均值，数值越接近 1 说明背景越接近纯白。

3. `highlight_mask_sparsity`
   高光掩码在整张图上的平均占比。它反映高光监督有多稀疏。

4. `highlight_foreground_ratio`
   高光像素占前景像素的比例。它反映前景内部可用于高光指导的有效监督密度。

5. `random_lighting_coverage`
   每个对象目录中 `random_lighting_*.png` 的数量相对 `total_view` 的覆盖率。

6. `image_name_match_ratio`
   对象目录中符合目标图像命名规则 `^(\d{3})_(\d{3})_.+\.png$` 的文件比例。

7. `missing_lighting_ratio`
   检查当前图像对应的 LDR、HDR-rescaled、HDR-raw 是否存在。其中 `any_missing` 在 ready 数据质量评估脚本里只依赖 LDR 和 HDR-rescaled，因此更接近训练可用性。

8. `mask_source_counts` 与 `mask_fallback_ratio`
   反映前景掩码来自显式 mask/alpha 还是白底阈值回退。

## 5. 统计配置与口径

当前质量报告使用的抽样配置为：

- `sample_objects = 12`
- `sample_images_per_object = 3`
- `total_view = 12`

因此，理论上每个数据集最多统计：

- 12 个对象级样本
- 36 个图像级样本

实际报告中四个子数据集均达到了这个采样上限，即每个数据集都统计了 12 个对象与 36 张图像。

需要特别说明的是，`dataset_quality.json` 中的 `total_object_count` 对应的是 ready 数据中训练 split 的对象总数，也就是 `READY_SUMMARY.json` 里的 `train_count_after_split`，而不是 `ready_count` 或 `trainable_count`。这意味着当前质量统计面向“实际进入训练的对象集合”，而不是所有曾通过预处理的对象。

从均值上看：

1. `ecommerce` 的前景占比最高，说明主体在画面中通常更大。
2. `landscape` 的前景占比最低，同时高光稀疏度最低，意味着这部分数据可能提供更弱、更稀疏的高光监督。

4. `landscape` 的高光稀疏度较低，但前景内高光占比不低，说明其困难更可能来自“前景本身较小”，而不是前景内完全缺乏高光。
5. `three_future` 在前景占比和高光稀疏度上处于中间位置，呈现出介于 `official_2000` 与 `landscape` 之间的监督密度。

## 8. 统计结果核查

### 8.1 采样数与配置一致

所有数据集都满足：

- `sampled_object_count = 12`
- `sampled_image_count = 36`

这与脚本配置 `12 objects x 3 images/object` 完全一致，说明采样逻辑正常执行，没有因为目录缺失或命名不匹配导致大面积跳样。

### 8.2 `total_object_count` 的口径正确

核查 `dataset_quality.json` 与 `READY_SUMMARY.json` 后，可得到：

- `official_2000`: `quality_total = 500`，等于 `train_count_after_split = 500`
- `ecommerce`: `quality_total = 716`，等于 `train_count_after_split = 716`
- `landscape`: `quality_total = 158`，等于 `train_count_after_split = 158`
- `three_future`: `quality_total = 553`，等于 `train_count_after_split = 553`

因此，当前质量评估统计的是“训练 split 中的对象”，这个口径是自洽的。

### 8.3 `image_name_match_ratio = 0.8889` 是预期结果

随机抽查四个数据集的对象目录后发现，每个对象目录通常包含 216 张 PNG：

- 192 张符合训练目标图像命名规则
- 12 张 `random_lighting_*.png`
- 12 张 `*_normals.png`

所以：

`image_name_match_ratio = 192 / 216 = 0.888888...`

这说明该指标反映的是“对象目录中混合存在辅助图像”，不是目标图像缺失或命名错误。

### 8.4 `hdr_raw_missing = 1.0` 不等于照明缺失

脚本 `assess_dataset_quality.py` 中的 `lighting_missing_flags()` 定义为：

- `ldr_missing`：检查 `LDR/object_id/target_filename`
- `hdr_rescaled_missing`：检查 `HDR_rescaled/object_id/target_filename`
- `hdr_raw_missing`：检查 `HDR_raw/object_id/target_filename`
- `any_missing`：只要 LDR 与 HDR-rescaled 都存在，就记为 0

抽查对象目录后发现，`HDR_raw` 目录通常存在，但其内部文件并不采用与目标图像逐张对应的命名方式。例如：

- `official_2000/HDR_raw/<object_id>/` 下常见文件名直接是对象 id
- `landscape` 与 `three_future` 的 `HDR_raw/<object_id>/` 目录存在，但可能为空目录

因此：

- `hdr_raw_missing = 1.0` 说明“按逐图同名匹配时找不到 HDR_raw 文件”
- `any_missing = 0.0` 说明“当前训练真正依赖的 LDR 与 HDR-rescaled 是完整的”

在当前论文和训练口径下，后者才是更重要的可训练性指标。

### 8.5 `mask_fallback_ratio = 0.0` 说明显式前景信息可用

`dataset/foreground_mask_utils.py` 中，脚本会优先尝试：

- alpha 通道
- 单独的 mask/alpha 图
- 若都失败，再回退到基于白背景阈值的掩码

当前四个子数据集的采样结果均为：

- `mask_fallback_ratio = 0.0`

这说明采样图像都能解析出显式前景掩码，不需要依赖回退策略。

### 8.6 自动质量告警为空

`assess_dataset_quality.py` 的 `derive_quality_flags()` 使用以下阈值：

- `background_whiteness < 0.9`
- `foreground_area_ratio < 0.1`
- `highlight_mask_sparsity < 0.01`
- `missing_lighting_ratio.any_missing > 0.01`
- `random_lighting_coverage < 0.5`
- `mask_fallback_ratio > 0.5`

本次四个数据集都没有触发任何 flag，说明至少在脚本定义的基础健康检查层面，没有发现明显异常。

### 8.7 `official_2000` 的 HDRI 口径需要区分“完整目录”和“ready 子集”

针对 `official_2000`，进一步检查实际目录、对象重叠关系以及 lighting 文件分布后，可以得到一个比原日志更准确的结论：

1. `training_img_data_official_2000` / `training_lighting_data_official_2000` 是一个混合目录，而不是单一来源的新渲染结果。
2. 这个混合目录中包含两部分对象：
   - 与当前 `training_img_data_subset` 重叠的 1000 个保留 official 基础对象
   - 新增补渲染并通过预处理的 526 个 official_2000 对象
3. 保留的 1000 个基础对象仍然保留了原始 official 数据中的大 lighting 集合；抽查重叠对象可见其单对象通常具有约 187 到 192 个 lighting condition。
4. 新增补渲染的 526 个对象则统一使用一个 17 项的替代 light pool。

这 17 个替代 HDRI 来自实际目录：

- `/4T/CXY/Neural_Gaffer_original/objaverse_lighting_domains/official_mixed/available`

该目录中的 17 个条目是软链接，指向：

- `demo/environment_map_sample`
- `demo/hdrmaps_for_3d`
- Blender 自带 `studiolights/world`

对应的 `metadata.json` 也明确写道：

- `Original official HDRI set is unavailable in-repo; using pooled local HDRIs from demo samples, theme lighting domains, and Blender world lights.`

因此，`official_2000` 里的 “official” 表示对象来源与对象协议，不应被理解为“新补渲染对象继续使用了完整官方 HDRI 集”。

更具体地说：

1. 完整目录 `training_lighting_data_official_2000` 是“旧 official lighting + 新 17-HDRI 补渲染对象”的混合体。
2. 当前 ready 导出的 `official_2000` 子集只链接了那 526 个新增补渲染对象，因此 ready 版本实际使用的 HDRI 池就是 17 个。
3. 也正因为如此，直接查看完整 `training_lighting_data_official_2000` 目录会得到很大的 lighting 去重数，而查看 ready 子集只会看到 17 个 HDRI，这两者并不矛盾，只是统计口径不同。

## 9. 对论文写作的可用结论

基于当前统计，可以在论文中较稳妥地写出以下几类判断：

1. ready 数据集在当前训练配置下具有稳定的前景掩码来源与完整的主照明文件组织，因此能够支持前景约束和 image-space 高光辅助监督。
2. 不同子数据集在前景尺度和高光密度上存在分布差异，这为分析数据域差异对高光监督难度的影响提供了定量依据。
3. `landscape` 的目标尺度更小、高光更稀疏，可作为相对困难的数据域；`official_2000` 与 `ecommerce` 则提供更密集的高光监督信号。
4. 当前质量结论应被视为“与主方法配置对齐的抽样质量快照”，而不是覆盖全部对象的最终普查。

不建议在论文中直接写出的强结论有：

1. 不建议仅凭这份抽样报告宣称某个子数据集“绝对更优”。
2. 不建议把 `hdr_raw_missing=1.0` 解读为照明资产不完整。
3. 不建议把当前统计外推成全量对象的严格总体分布。

## 10. 局限与后续建议

当前报告仍有三点局限：

1. 抽样规模较小，每个数据集只抽样了 12 个对象、36 张图像。
2. 统计值与当前训练配置绑定，如果后续调整高光阈值、relative mode 或前景阈值，结果会随之变化。
3. `image_name_match_ratio` 与 `hdr_raw_missing` 受目录组织和命名方式影响较大，解释时必须结合脚本定义。

如果后续希望把这部分做成更正式的论文证据，建议优先做两件事：

1. 将 `sample_objects` 从 12 提高到至少 48，与脚本默认值一致，降低抽样波动。
2. 将 ready 数据质量报告与论文正文表格共用同一套数据导出脚本，减少手工转抄风险。

## 11. 最终结论

综合预检查脚本、ready 数据验证脚本和质量评估脚本的结果，可以认为当前四个子数据集已经满足论文当前阶段对训练可用性和监督信号质量的基本要求。

更具体地说：

1. 数据读取链路是通的。
2. 前景掩码是可信的。
3. 背景白度足够高。
4. 高光监督信号存在且不同子域间存在可分析差异。
5. 现有统计整体自洽，没有发现会直接推翻当前数据协议的异常。

因此，这部分数据可以作为论文中“数据协议与质量控制”的支撑材料使用，但表述上应坚持“阶段性、配置对齐、抽样评估”这三个限定词。
