# 2026-03-31 高光专项评测与对比实验设计（Neural_Gaffer）

这份文档用来回答一个很具体的问题：

“如果我们要证明当前方法在高光（highlight / specular response）上确实有改进，应该看什么指标、怎么组织对比实验、论文里怎么展示才最有说服力？”

结论先写在前面：

1. “不能只跑总分”这个判断是对的。
2. 但候选指标里有些适合直接采用，有些只能作为辅助，有些需要改名或降级。
3. 对当前仓库最稳妥的做法不是引入一堆听起来新的指标，而是把现有 `uu/us/ra + highlight mask + assets/panel` 流程扩成一套“全局指标 + 高光专项指标 + 诊断图”的证据链。

---

## 1. 对你提出的指标逐条判断

### 1.1 定性分析：高光收敛度

这个方向是合理的，而且应该保留。

真正值得看的不是“亮不亮”本身，而是下面 4 个现象：

1. 高光是否过曝到直接 clipping
2. 高光是否在斜射光下被抹成一大片发灰的亮斑
3. 高光峰值位置是否偏移
4. 高光边界是否过宽或过散

对当前项目来说，这类图最好优先在：

1. `ra`（random-lighting）里选 hardest case
2. `uu` 里选 unseen object + unseen lighting 的尖锐高光 case

因为这两个设置最容易把“高光学得不稳”的问题暴露出来。

### 1.2 定性分析：材质一致性

这个方向也合理，但要加一个前提：

只有在样本材质标签相对可信，或者你能人工筛出“金属 / 塑料 / 木材”三组对象时，这个结论才值得写进正文。

原因很简单：

1. 金属高光带环境色，是材质与反射共同作用的结果
2. 塑料高光更接近白色，是更经典的 dielectric specular
3. 木材通常高光更弱、更宽，很多 case 更接近漫反射主导

所以这个分析很适合作为：

1. 人工精选定性图
2. 附录里的材质子集对比

但不建议在没有材质标注的全量验证集上直接把“颜色偏白/偏色”写成强结论。

### 1.3 LPIPS / DINOv2 Score

这个建议只有一半适合直接保留。

`LPIPS`：

1. 适合保留
2. 当前仓库本来就已经在验证里计算 `LPIPS`
3. 但最好报告两种版本：
   - 全图 LPIPS
   - foreground 或 highlight-focused LPIPS

原因是全图 LPIPS 仍然会被大量非高光区域稀释。

`DINOv2`：

1. 可以作为辅助，不建议当主指标
2. 它更像“语义/身份保持”度量，而不是专门衡量高光细节
3. 对“物体还是不是原来那个物体”有帮助
4. 但对“高光有没有过曝、有没有扩散、有没有漂移”并不敏感

更稳妥的说法是：

1. 正文主指标仍然用 `PSNR / SSIM / LPIPS + highlight-specific metrics`
2. `DINOv2 feature distance` 放附录或补充材料

### 1.4 Light Stability Score（你写的 2026 新指标）

这个提法需要明显降级。

原因不是它没意义，而是它在当前任务里容易被误用。

更准确地说：

1. “Light Stability Score” 这个名字近期确实在 `Hi-Light` 这类视频重光照工作里出现过
2. 但它主要是在视频设置里衡量 temporal coherence / lighting stability
3. 当前 `Neural_Gaffer` 主线是单图 object relighting，不是视频 relighting

所以不建议在单图论文里直接把它写成一个现成标准指标。

更合适的做法是：

1. 如果你要做“同一物体跨多光照是否稳定”的分析，可以自己定义一个新指标
2. 但名字最好写成：
   - `Cross-light Consistency Score (ours)`
   - `Highlight Response Stability (ours)`
3. 并明确给出定义，而不是直接借用视频论文里的术语

### 1.5 HDR 误差

这个指标只有在你手里真的有对象图像级 HDR / linear ground truth 时才成立。

对当前仓库要特别注意这一点：

1. 现在验证样本 `gt_path` 是 PNG
2. 光照图有 `HDR_rescaled / HDR_normalized`
3. 但这不等于“物体重光照结果本身有对象级 HDR GT”

所以：

1. 如果比较的是当前 `validation_data/images/.../*.png`，就不要写成 “HDR RMSE”
2. 更诚实的写法应该是：
   - `highlight-region RMSE`
   - `linearized-LDR highlight RMSE`（如果你做了线性化近似）
3. 只有换到真正提供 HDR target object image 的数据集时，才能把它升级成 HDR 误差

## 2. 对当前项目最推荐的指标层次

建议把指标分成三层，而不是只堆一张大表。

### 2.1 第一层：全局质量指标

这层继续保留，目的是证明方法没有靠“只优化高光”去牺牲整体质量。

推荐保留：

1. `PSNR`
2. `SSIM`
3. `LPIPS`

这些指标继续按现有 `uu / us / ra / tu / train` 或至少 `uu / us / ra` 报。

### 2.2 第二层：高光专项指标

这一层才是证明“高光改进”的主战场。

对当前仓库最值得上的指标是：

1. `highlight_psnr`
   - 只在 GT-derived highlight region 内算 PSNR
2. `highlight_rmse`
   - 只在 GT-derived highlight region 内算 RMSE
3. `highlight_mse_ratio`
   - `highlight_mse / non_highlight_mse`
   - 当前训练验证逻辑里已经有非常接近的统计
4. `highlight_mask_iou`
   - 预测高光区域与 GT 高光区域的重叠程度
5. `highlight_area_abs_error`
   - 看高光是过散还是过窄
6. `highlight_centroid_distance`
   - 看高光峰值位置有没有漂
7. `highlight_saturated_ratio_abs_error`
   - 看是否过曝 / clipping
8. `highlight_p95_luma_abs_error`
   - 看强高光尾部是否被压扁或炸白
9. `highlight_chroma_l1_on_gt_mask`
   - 用来辅助分析高光颜色是否接近 GT

### 2.3 第三层：身份与稳定性辅助指标

这层不建议放到最前面，但很适合辅助解释。

推荐顺序：

1. `foreground LPIPS`
2. `highlight-crop LPIPS`
3. `DINOv2 feature distance` 或更强的人感相似度指标
4. `Cross-light Consistency Score (ours)`，前提是你真的做多光照 sweep

## 3. 当前仓库里已经有的基础，不需要重搭

这点很关键，因为说明这套实验不是空想。

当前仓库已经有三块能直接复用的能力：

### 3.1 样本级对比管线

现有脚本链路已经是：

1. `scripts/create_relighting_comparison_manifest.py`
2. `scripts/run_ours_on_comparison_manifest.py`
3. `scripts/run_official_demo_on_comparison_manifest.py`
4. `scripts/export_relighting_comparison_assets.py`
5. `scripts/build_relighting_comparison_panel.py`

也就是说：

1. 样本抽取
2. 多方法预测
3. 资产导出
4. panel 生成

这些都已经具备。

### 3.2 现有高光定义

当前主线代码里已经有：

1. foreground-priority mask
2. white background fallback
3. foreground-only quantile threshold
4. blur-only threshold estimation
5. local relative highlight definition

这意味着：

高光专项评测不应该再换一套完全不同的高光定义，否则会让训练目标和评测口径脱节。

### 3.3 现有验证里已经有高光损失统计

`neural_gaffer_training.py` 目前验证阶段已经在算：

1. `highlight_mse`
2. `non_highlight_mse`
3. `highlight_mse_ratio`

所以“单独报告高光区域指标”并不是另起炉灶，而是把已有思想延伸到样本级对比实验里。

## 4. 推荐的对比实验组织方式

### 4.1 定量表怎么摆

最推荐的正文结构是两张表，而不是一张表把所有指标塞满。

#### 表 1：全局质量表

列：

1. method
2. `uu`
3. `us`
4. `ra`
5. optional `tu`

每个 split 报：

1. `PSNR`
2. `LPIPS`
3. `SSIM`

作用：

1. 证明整体质量没有退化
2. 证明 `ra` 确实是困难 split

#### 表 2：高光专项表

建议只对 hardest subset 报，避免正文太挤。

推荐子集：

1. `ra-hard`
2. `uu-specular-hard`

每个子集报：

1. `highlight_psnr`
2. `highlight_rmse`
3. `highlight_mask_iou`
4. `highlight_area_abs_error`
5. `highlight_saturated_ratio_abs_error`
6. `highlight_p95_luma_abs_error`

作用：

1. 直接证明改进发生在高光区，而不是总分偶然波动

### 4.2 定性图怎么摆

最推荐的不是只放一整页大 panel，而是“总图 + 局部放大 + 诊断图”三件套。

#### 图 A：主对比图

每行列顺序建议：

1. Input
2. Baseline
3. Ours
4. GT
5. Target lighting

行选择：

1. 金属
2. 塑料
3. 木材/陶瓷
4. 再加 2 个 `ra` hardest case

#### 图 B：高光局部放大图

每个样本只截最关键的一块 highlight ROI。

这张图重点看：

1. baseline 是否炸白
2. baseline 是否发灰发糊
3. ours 是否更接近 GT 的峰值位置和宽度

#### 图 C：诊断图

利用现有 stage output 思路，建议每个 case 再给一组诊断行：

1. foreground mask
2. local-relative brightness
3. GT highlight mask
4. Pred highlight mask
5. absolute difference heatmap

这组图的作用是让 reviewer 看懂：

“改进不只是视觉主观感觉，而是高光区域定位和响应都更接近 GT。”

### 4.3 如果你要讲“稳定性”

那就不要只做单点图。

建议固定：

1. 同一个 `object_id`
2. 同一个 `view_idx`
3. 选 6 到 12 个 target lighting

然后画：

1. `highlight area` 随 lighting 变化的曲线
2. `highlight centroid` 轨迹误差
3. `highlight peak luminance` 的 GT-vs-pred 散点图

这时你才可以合理地说你在测“cross-light stability”。

## 5. 推荐的最小可执行实验清单

如果目标是“最快拿到有说服力的结果”，建议按下面顺序做。

### 5.1 第一轮：论文主结果最小版

方法：

1. corrected baseline
2. full main method

样本：

1. `uu`: 12 到 24 个
2. `us`: 12 到 24 个
3. `ra`: 12 到 24 个

输出：

1. 全局指标表
2. 高光专项指标表
3. 6 样本总图
4. 6 个高光局部放大图

### 5.2 第二轮：材质子集图

人工从样本中筛出：

1. metal
2. plastic
3. wood / ceramic

每组 2 到 4 个 case 即可。

输出：

1. 材质对比图
2. 高光颜色 / clipping 的案例说明

### 5.3 第三轮：稳定性子实验

固定 2 到 3 个对象，每个对象做 6 到 12 个光照 sweep。

输出：

1. `highlight area` 曲线
2. `highlight centroid distance` 曲线
3. `peak luminance error` 曲线

这轮更适合附录，不一定非放正文。

## 6. 当前仓库里的落地脚本建议

为了让这件事马上能跑，我补了一个 manifest 级高光专项评测脚本：

- `scripts/evaluate_highlight_metrics_on_assets_manifest.py`

它直接吃 `export_relighting_comparison_assets.py` 生成的 `exported_assets_manifest.json`，并输出：

1. 全图 / foreground / highlight 区域指标
2. `highlight_mask_iou`
3. `highlight_area_abs_error`
4. `highlight_centroid_distance`
5. `highlight_saturated_ratio_abs_error`
6. `highlight_p95_luma_abs_error`
7. `lpips_full / lpips_foreground / lpips_highlight_crop`

推荐用法示例：

```bash
python Neural_Gaffer/scripts/evaluate_highlight_metrics_on_assets_manifest.py \
  --assets-manifest Neural_Gaffer/logs/official_demo_eval/official_release_paper6_assets_v1/exported_assets_manifest.json
```

如果你后面把 baseline / ours / official-demo 都放进同一个 assets manifest，这个脚本就可以直接出方法间对比摘要。

## 7. 最后给一个明确判断

如果目标是“证明高光改进”，那你的原始思路整体是有道理的，但建议改成下面这版口径：

1. 保留：
   - visual comparison
   - material consistency
   - LPIPS
   - highlight-region RMSE / PSNR
2. 降级：
   - DINOv2 只做辅助 identity metric
3. 改名：
   - 不直接写 `Light Stability Score`
   - 改成 `Cross-light Consistency Score (ours)` 或 `Highlight Response Stability (ours)`
4. 暂不直接使用：
   - HDR RMSE，除非你换到真正有 HDR object GT 的数据

一句话概括最推荐的方案：

“先用 `全局指标 + 高光专项指标 + 高光局部放大图 + 诊断图` 证明改进真实存在；如果还有预算，再补材质子集和跨光照稳定性曲线。”
